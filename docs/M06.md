# M06 — Check-in académico, consentimiento y admisión

## Propósito

- Permite que un paciente adulto, actuando por cuenta propia, complete un check-in administrativo para una cita confirmada.
- Expone progreso, consentimiento de demostración, preflight técnico declarativo y estado `Ready`.
- El servidor decide el estado final; Flutter solo presenta y envía declaraciones.
- Alcance actual: demo académico, datos sintéticos, sin atención médica real.

No hace:

- No realiza triaje clínico, diagnóstico, urgencias ni recomendaciones.
- No habilita tutores/dependientes ni `GuardianLink`.
- No verifica identidad con documentos, biometría o medios.
- No captura cámara, micrófono, video, imágenes ni grabaciones.
- No emite tokens de videoconsulta; eso pertenece a M07.
- No constituye consentimiento legal o clínico para producción.

## Estructura

Backend (`api/src`):

- `Telemedicina.Api/Features/Appointments/CheckInContracts.cs`: DTOs de solicitud, snapshot del paciente y proyección redactada para Admission.
- `Telemedicina.Api/Features/Appointments/CheckInPolicy.cs`: versión de configuración/consentimiento, hash, ventana UTC, mayoría de edad y máquina de estados.
- `Telemedicina.Api/Features/Appointments/CheckInController.cs`: endpoints autenticados, autorización por rol, locks, idempotencia, recomposición de estado y auditoría.
- `Telemedicina.Api/Infrastructure/Persistence/Migrations/010_academic_check_in.sql`: tabla, constraints, índices y vista `ready_check_ins`.
- `Telemedicina.Api/Features/Appointments/AppointmentsController.cs`: invalida el check-in al cancelar o reprogramar la cita.
- `Telemedicina.Api/Features/Admission/AdmissionController.cs`: mantiene la separación de la proyección administrativa.
- `Telemedicina.Api/Infrastructure/Persistence/Seeding/DemoDataReset.cs`: incluye el estado H06 en el reset sintético.

Flutter (`app/src`):

- `lib/features/appointments/data/appointment_repository.dart`: modelos, lectura de requisitos y POST idempotente.
- `lib/app/application/patient_controller.dart`: carga del detalle, generación/reutilización de clave idempotente y limpieza por sesión.
- `lib/features/appointments/presentation/appointments_view.dart`: diálogo de check-in y estados visibles.
- `lib/features/appointments/presentation/appointment_session_guard.dart`: retira overlays y respuestas de sesiones obsoletas.
- `lib/app/presentation/patient_shell.dart`: conecta el flujo con la pantalla de citas.

Pruebas:

- `api/src/Telemedicina.Tests/Contracts/H06UnitChecks.cs`: política, estados, adulto/self, consentimiento y autorización/redacción.
- `api/src/Telemedicina.Tests/Contracts/H06DbChecks.cs`: migración, unicidad concurrente, guards de `Ready`, vista e invalidación.
- `app/src/test/features/appointments/*`: repositorio, controlador y widget del flujo.

## API pública

Todos los endpoints están bajo `/api/v1` y requieren sesión.

- `GET /appointments/{id}/check-in-requirements` (`Patient`): devuelve el snapshot de la cita propia, requisitos, consentimiento y bloqueadores; cita ajena responde `404`.
- `POST /appointments/{id}/check-in` (`Patient`): recibe `version`, checklist, consentimiento y preflight; exige `Idempotency-Key` UUID y devuelve `409` en conflicto, ventana cerrada, perfil incompleto, menor o replay invalidado.
- `GET /admission/appointments/{id}/check-in-status` (`Admission`): devuelve solo estado, versiones y timestamps operativos; no expone declaraciones, texto/hash de consentimiento ni preflight.

Tipos reutilizables:

- `CheckInRequest`: versión optimista y cinco declaraciones booleanas; `ConsentVersion` debe ser `1`.
- `PatientCheckInSnapshot`: estado, ventana, checklist, consentimiento y bloqueadores para el paciente.
- `AdmissionCheckInStatus`: proyección mínima para Admission.
- `CheckInPolicy.OpensAt/ClosesAt/InWindow`: ventana inclusiva de `-30/+15` minutos respecto al inicio UTC.
- `CheckInPolicy.IsAdultSelf`: exige `birthDate` ISO `yyyy-MM-dd` y edad mínima de 18 años.
- `CheckInPolicy.State`: calcula `NotStarted`, `InProgress`, `Verified`, `Ready`, `Rejected` o `Expired` con entradas ya validadas.

Los métodos del controlador son síncronos y ejecutan transacciones PostgreSQL. El repositorio Flutter expone `Future`; las llamadas ocurren en el isolate de UI y se ignoran si cambia `sessionGeneration`.

## Dependencias

- M04/M05: cita, estado `Confirmed`, versión, cancelación y reprogramación.
- M02: perfil y cálculo de completitud/fecha de nacimiento.
- Identidad/autorización: sesión, rol `Patient`/`Admission` y aislamiento horizontal.
- PostgreSQL/Npgsql: transacciones, `FOR UPDATE/FOR SHARE`, advisory locks, constraints e índices parciales.
- Auditoría existente: registra acciones y resultados sin contenido privado.
- Tabla `idempotency`: vincula usuario, clave, hash de solicitud y snapshot histórico.
- Flutter `ApiClient`: sesión, errores y UUID de idempotencia.
- No depende de proveedor externo de video, correo ni SDK clínico.

## Decisiones de diseño

- **Demo académico no clínico.** Se eligieron declaraciones administrativas porque no existe un paquete clínico/legal aprobado; se descartó inventar preguntas, reglas o recomendaciones.
- **Solo adulto Self.** Se exige mayoría de edad calculada desde `birthDate`; se descartó tutoría porque no existe `GuardianLink` verificable.
- **Consentimiento fijo v1 + hash.** El texto y hash están versionados en código y en la constraint SQL; se descartó texto editable o legal real.
- **Ventana UTC inclusiva `-30/+15`.** La regla es determinista y comprobable; fuera de ella no se alcanza `Ready`.
- **`Ready` solo en servidor.** Flutter no envía outcome ni timestamps confiables; se descartó calcular elegibilidad localmente.
- **GET proyecta, no muta el agregado.** Expiración, invalidación y cambios de perfil se reflejan al leer sin incrementar versiones; se descartó mutar estado desde una lectura.
- **Locks + versión + idempotencia.** Evitan duplicados y carreras entre check-in, cancelación y reprogramación; el replay recompone el estado bajo locks y no devuelve un snapshot `Ready` obsoleto.
- **Vista `ready_check_ins` como contrato de consumo.** H07 debe consumir solo filas que mantienen todos los gates administrativos, cita confirmada, versiones y ventana.
- **Admission redactado.** Admission recibe metadatos operativos, no el contenido del cuestionario ni el consentimiento.
- **Sin medios.** El preflight es declarativo; cámara, micrófono, video y grabación quedan fuera.

## Problemas encontrados y soluciones

- Replay idempotente de r2 podía devolver `Ready` histórico tras cancelar/reprogramar; r3 recompone bajo locks y responde `CHECK_IN_INVALIDATED`.
- La expiración podía mostrar una versión fantasma cuando el intento ya estaba expirado; la lectura actual proyecta el estado sin incrementar la versión persistida.
- La vista inicial confiaba demasiado en `state='Ready'`; ahora repite checklist, consentimiento, preflight, perfil/cita, ventana y versiones.
- La API de GET usa locks compartidos y registra auditoría, aunque no modifica el agregado; esto debe considerarse al medir lecturas.
- El consentimiento aceptado no se desmarca con un envío posterior en falso: la aceptación persistida se conserva.
- El test DB está protegido por `MILESTONE_TEST_SYNTHETIC=1` y `ASPNETCORE_ENVIRONMENT=Development`; sin esas variables termina en `OPT_IN` por diseño.

Prioridad media:

- No hay interfaz de portal específica para consultar el estado H06; esto es intencional y está fuera del alcance cerrado.
- No hay rollback SQL automático para la migración 010; revertir código no revierte datos ya migrados.
- `ready_check_ins` presupone que solo el backend puede escribir directamente en PostgreSQL.
- La configuración, consentimiento y hash están fijos en código; una futura versión debe definir publicación/supersesión antes de externalizarlos.

Fuera de alcance:

- Tutoría/dependientes, triaje clínico real, identidad documental, retención legal, video, historia clínica y uso con pacientes reales.

## Cómo probarlo

Desde la raíz:

```bash
dotnet build api/src/Telemedicina.sln --configuration Release
python3 api/src/Tools/run_local.py --configuration Release --no-build -- --migrate
python3 api/src/Tools/run_local.py --configuration Release --no-build -- --inspect
```

Pruebas API/unitarias:

```bash
dotnet run --no-build --configuration Release --project api/src/Telemedicina.Tests/Telemedicina.Tests.csproj
MILESTONE_TEST_SYNTHETIC=1 ASPNETCORE_ENVIRONMENT=Development \
  dotnet run --no-build --configuration Release \
  --project api/src/Telemedicina.Tests/Telemedicina.Tests.csproj -- --h06-db-tests
```

La prueba DB cubre migración 010, vista, constraint de `Ready`, unicidad concurrente, invalidación y replay idempotente. Las pruebas unitarias cubren estados, ventana, adulto/self, consentimiento y autorización/redacción.

Flutter:

```bash
cd app/src
flutter pub get
flutter analyze
flutter test
```

La validación manual usa API y PostgreSQL sintéticos, una cita confirmada dentro de ventana y un paciente adulto. En Android físico, después de iniciar la API:

```bash
adb reverse tcp:5000 tcp:5000
flutter run -d <device-id> --dart-define=API_BASE_URL=http://127.0.0.1:5000/api/v1
```

Flujo manual: abrir una cita, completar parcialmente el diálogo, comprobar `InProgress`, completar checklist/consentimiento/preflight, comprobar `Ready`, y después verificar que cancelar o reprogramar invalida el check-in.
